Scope filter: only requirements that bind **a server** (or that the server must anticipate from

authorization, resources/prompts/completion/sampling/elicitation/roots rules are omitted unless

## (b) Per-request metadata

All keys live in **`params._meta`** of the request (type `RequestParams { _meta: RequestMetaObject }`).
`_meta` is **non-optional** in `RequestParams` (schema.ts line ~161: `_meta: RequestMetaObject;`), and every
modern request type declares `params` non-optional (e.g. `DiscoverRequest { params: RequestParams }`,
`PaginatedRequest { params: PaginatedRequestParams }`, `CallToolRequest { params: CallToolRequestParams }`).

## (c) `server/discover`

Request (exact official example, `examples/DiscoverRequest/server-discover-request.json`):
```json
{"jsonrpc":"2.0","id":"discover-1","method":"server/discover",
 "params":{"_meta":{"io.modelcontextprotocol/protocolVersion":"2026-07-28",
   "io.modelcontextprotocol/clientInfo":{"name":"ExampleClient","version":"1.0.0"},
   "io.modelcontextprotocol/clientCapabilities":{}}}}
```
Result (`schema.ts`: `DiscoverResult extends CacheableResult` ⇒ `extends Result`):

| field | required? | type |
|---|---|---|
| `resultType` | schema-required (`Result`) | `"complete"` |
| `supportedVersions` | schema-required | `string[]` |
| `capabilities` | schema-required | `ServerCapabilities` (for us: `{"tools":{}}` or `{"tools":{"listChanged":false}}`) |
| `ttlMs` | schema-required (`CacheableResult`), MUST ≥ 0 | number (integer ms) |
| `cacheScope` | schema-required (`CacheableResult`) | `"public"` \| `"private"` |
| `instructions` | optional | string |
| `_meta["io.modelcontextprotocol/serverInfo"]` | SHOULD | `Implementation` (`name`, `version` required; `title`, `description`, `websiteUrl`, `icons` optional) |

There is **no** top-level `serverInfo` and **no** `protocolVersion` field in `DiscoverResult` (unlike
`InitializeResult`).

Proposed bridge answer:
```json
{"jsonrpc":"2.0","id":"discover-1","result":{
  "resultType":"complete",
  "supportedVersions":["2026-07-28"],
  "capabilities":{"tools":{"listChanged":false}},
  "ttlMs":0,"cacheScope":"public",
  "_meta":{"io.modelcontextprotocol/serverInfo":{"name":"plasma-mcp-bridge","version":"<ver>"}}}}
```
(See F-41 on what to put in `supportedVersions`, and F-52 on choosing `ttlMs`.)

Official -32022 example (`examples/UnsupportedProtocolVersionError/unsupported-version.json`):
```json
{"jsonrpc":"2.0","id":1,"error":{"code":-32022,"message":"Unsupported protocol version",
  "data":{"supported":["2026-07-28","2025-11-25"],"requested":"1900-01-01"}}}
```
Official -32602 / -32601 / -32700 examples: `{"code":-32602,"message":"Unknown tool: invalid_tool_name"}`,
`{"code":-32602,"message":"Invalid cursor"}`, `{"code":-32601,"message":"Prompts not supported","data":{"reason":"Server does not support the prompts capability"}}`,
`{"code":-32700,"message":"Parse error: Invalid JSON"}`.

**Check ordering is unspecified**: the spec does not say whether a request with an unsupported
version *and* missing `clientCapabilities` gets -32022 or -32602, nor whether an unknown method with
an unsupported version gets -32601 or -32022. Recommendation: (1) frame/JSON-RPC validity
(-32700/-32600), (2) `protocolVersion` present & string? else era rules below, (3) version supported?
else -32022 — this guarantees the stdio probe (F-42) works even if a future client's `_meta` shape
changes, (4) `clientCapabilities` present & object? else -32602, (5) method known? else -32601,
(6) method params → -32602.

## Corrections to our design §7

Point by point against `docs/superpowers/specs/2026-10-01-remediation-core-design.md` §7.

1. **"protocole sans état : plus de handshake initialize/notifications/initialized"** — RIGHT for the
   modern era (changelog Major 2). INCOMPLETE: for a dual-era server `initialize` is *not* removed;
   it "selects legacy semantics, scoped to the stdio process" (F-14), and "Legacy × Dual-era: Works.
   The server answers `initialize`" (F-16). Also MUST NOT let that legacy state influence modern
   requests (F-19).
2. **"server/discover : obligatoire"** — RIGHT (F-5/F-34). INCOMPLETE: `DiscoverResult` extends
   `CacheableResult`, so it **also requires `ttlMs` and `cacheScope`** (F-37), not just `tools/list`.
   Exact required fields: `resultType`, `supportedVersions`, `capabilities`, `ttlMs`, `cacheScope`;
   `_meta["io.modelcontextprotocol/serverInfo"]` SHOULD; `instructions` optional. No top-level
   `serverInfo`/`protocolVersion`. The discover request itself is version-checked (F-42).
3. **"chaque requête porte `_meta["io.modelcontextprotocol/protocolVersion"]` et `clientCapabilities`"**
   — PARTLY WRONG on the key name: the capabilities key is
   **`params._meta["io.modelcontextprotocol/clientCapabilities"]`**, not `clientCapabilities` (and not
   `params.clientCapabilities`). Both live in `params._meta` (F-22/F-23). "-32602 if missing" is
   RIGHT and is a MUST (F-24). Additional optional keys: `io.modelcontextprotocol/clientInfo`
   (SHOULD, client), `io.modelcontextprotocol/logLevel` (deprecated), `progressToken`.
   Note `params` itself becomes mandatory for modern requests.
4. **"tous les résultats portent `resultType` obligatoire"** — RIGHT (F-43); value `"complete"` for
   everything the bridge returns, including `isError: true` tool results (F-47).
   **"`tools/list` porte `ttlMs` et `cacheScope`"** — RIGHT names, REQUIRED (schema) on
   `tools/list` and `server/discover` (F-48/F-37); `ttlMs` MUST be ≥ 0 (F-49), `cacheScope` ∈
   `"public"|"private"`. NOT on `tools/call` (F-55). MISSING from §7: servers SHOULD put
   `_meta["io.modelcontextprotocol/serverInfo"]` in **every** result (F-30).
5. **"`ping` et `logging/setLevel` sont retirés"** — RIGHT (changelog Major 5). Also removed:
   `notifications/roots/list_changed`. Consequence for modern mode: `ping` → -32601 (F-88). Logging
   is additionally deprecated; bridge must not declare `logging` and MUST NOT emit
   `notifications/message` without `logLevel` (F-90/F-92). "ping reste servi aux requêtes
   historiques" — consistent with the spec (legacy semantics are per the negotiated legacy version).
6. **"`UnsupportedProtocolVersionError` (-32022), qui nomme les versions supportées"** — RIGHT but
   INCOMPLETE: `data` has two **required** fields, `supported: string[]` **and**
   `requested: string` (F-81). What to list in `supported` is AMBIGUOUS for a dual-era server
   (F-41): the official example lists a legacy version (`"2025-11-25"`) next to `"2026-07-28"`.
7. **"un client dual-era sonde server/discover … se rabat sur initialize si le serveur répond par une
   autre erreur ou ne répond pas"** — RIGHT (F-8/F-9). Precision: the probe carries the client's
   preferred modern version; "recognized modern error" (e.g. -32022) ⇒ client stays modern and
   does not fall back. Keeping `server/discover` at -32601 until F is fully delivered is CORRECT
   (any non-modern error ⇒ legacy, F-9/F-10), and the warning against a partial `DiscoverResult` or
   a -32020…-32099 code is well-founded (and F-84 forbids undefined codes in that range anyway).
8. **Aiguillage "moderne si porte `_meta[...protocolVersion]`"** — CONSISTENT with "A request
   carrying modern per-request `_meta` is served statelessly" (F-13). Precisions:
   - The spec does not define the discriminator precisely; keying on the presence of the
     `io.modelcontextprotocol/protocolVersion` key in `params._meta` is a reasonable reading. A
     present-but-non-string value should be -32602 (malformed), not legacy.
   - A request *without* modern `_meta` and no prior `initialize` (e.g. raw `tools/list`): strict
     modern reading = malformed (-32602, F-24); legacy reading = implementation-defined pre-init
     behavior (F-10, "commonly -32601 or -32602 … or not at all"; matrix: legacy servers may
     "process an era-ambiguous method under legacy semantics"). Keeping §6 historical behavior is
     allowed; it is the dual-era choice.
   - Order of checks (version vs capabilities vs method) is unspecified; recommend version first
     (see end of section (f)).
   - `notifications/cancelled` carries no era metadata (F-33): handle identically for both eras.
9. **"Une version moderne non supportée → -32022"** — RIGHT, and it applies to **every** modern
   method including `server/discover` (F-4/F-42), with "unsupported" meaning anything the server has
   not chosen to support, known or unknown. Open point (F-41): a `_meta` request carrying a
   *legacy* version string (e.g. `"2025-11-25"`) — the spec is silent.
10. **"Un `initialize` reçu en mode moderne : comportement à fixer en F0"** — RESOLVED: the SHOULD
    about naming supported versions in the `initialize` error applies only to a server "that
    supports only modern versions" (F-12). A dual-era server answers `initialize` normally under
    legacy semantics (F-14/F-16). For an `initialize` whose `params.protocolVersion` is
    `"2026-07-28"` (or later): `initialize` is a legacy-only method, so answer with ordinary legacy
    negotiation → latest legacy version (`2025-11-25`). **Do not add `"2026-07-28"` to
    `mcp::supportedProtocolVersions()`** used by `negotiateProtocolVersion` (src/mcp/protocolversion.cpp),
    or `initialize` would "negotiate" a version that has no `initialize`. Keep two separate lists
    (legacy-negotiable vs modern). An `initialize` that *also* carries modern `_meta` is not
    addressed by the text; treating it as legacy (it's not a modern method) is the coherent choice;
    the alternative (modern → -32601) is the "Legacy × Modern" behavior and would break that client.
11. **Missing from §7 entirely:**
    - Cancellation on stdio: server **MUST NOT send any further messages** for a cancelled request
      (F-95) — stronger than the legacy SHOULD; verify the runner suppresses the late response.
    - Error-code policy: no codes -32020…-32099 except -32020/-32021/-32022 with their meaning;
      SHOULD NOT use -32000…-32019; never -32002/-32042 (F-84–F-86).
    - `subscriptions/listen` (core method, F-103): decide between a minimal implementation (ack with
      empty filter, hold open until `notifications/cancelled`, graceful completion on shutdown) and
      -32601. Text is ambiguous.
    - MRTR: nothing to implement; just never return `input_required` and ignore stray
      `inputResponses`/`requestState` on `tools/call` (F-100–F-102).
    - `tools/list` SHOULD be deterministic in order (F-57) and MUST NOT vary per connection (F-56);
      `inputSchema` root `type:"object"` required (F-61); no `execution`/`taskSupport` in modern
      output (F-66).
    - `cursor` on `tools/list`: bridge doesn't paginate; any cursor is invalid → -32602 SHOULD (F-59).
    - Tests in §7 should add: discover carries `ttlMs`/`cacheScope`/`serverInfo` in `_meta`; -32022
      `data.requested`; modern `ping` → -32601; modern `initialize`-less flow never depends on a
      previous `initialize`; cancelled modern `tools/call` produces no response; `logLevel` present
      produces no `notifications/message`; probe with unsupported version → -32022 (not -32601).

## Minimal conformant feature set for plasma-mcp-bridge (2026-07-28, stdio, tools-only, dual-era)

**Must implement**
1. Per-request era switch: request with `params._meta["io.modelcontextprotocol/protocolVersion"]`
   ⇒ modern path; `initialize` ⇒ legacy path (unchanged §6 behavior, negotiation list without
   2026-07-28). (F-13, F-14, F-16)
2. Modern validation: `protocolVersion` string; unsupported ⇒ -32022 with
   `data:{supported:[…], requested:"<v>"}`; `io.modelcontextprotocol/clientCapabilities` object
   present ⇒ else -32602. (F-4, F-24, F-81)
3. `server/discover` ⇒ `{resultType:"complete", supportedVersions, capabilities:{tools:{…}}, ttlMs≥0,
   cacheScope, _meta:{"io.modelcontextprotocol/serverInfo":{name,version}}}`. (F-5, F-36–F-40)
4. Modern `tools/list` ⇒ legacy payload + `resultType:"complete"`, `ttlMs`, `cacheScope`,
   deterministic order, no `nextCursor`. (F-43, F-48, F-57)
5. Modern `tools/call` ⇒ legacy payload + `resultType:"complete"`; tool errors as `isError:true`;
   unknown tool -32602. (F-43, F-47, F-69, F-70)
6. Modern requests (carrying modern `_meta`) for unknown/removed methods (`ping`,
   `logging/setLevel`, prompts/resources/completion) ⇒ -32601. `initialize` always takes the
   legacy path (see Corrections §10). (F-80, F-88)
7. Cancellation: `notifications/cancelled` honored for both eras; after cancellation emit nothing
   for that id. (F-95)
8. Error-code hygiene: only -32700/-32600/-32601/-32602/-32603/-32022 emitted. (F-84–F-86)
9. stdio framing unchanged (UTF-8, one message per line, stdout clean, stderr logs, exit on EOF).
   (F-107–F-113)

**SHOULD (cheap, do it)**
- `_meta["io.modelcontextprotocol/serverInfo"]` on every modern result (F-30).
- -32602 for any `cursor` on `tools/list` (F-59).

**May skip (with justification)**
- MRTR / `InputRequiredResult`: "Servers **MAY** respond to any supported client request with an
  `InputRequiredResult`." (F-100)
- Pagination: `nextCursor` is optional ("An optional `nextCursor` field if more results exist").
- Progress notifications: "The server **MAY** send progress notifications". (F-98)
- Logging: deprecated, "New implementations **SHOULD NOT** adopt it". (F-91)
- `instructions` in discover: "Optional". (F-39)
- `structuredContent`/`outputSchema`: optional fields. (F-68, F-72)
- `listChanged` notifications: only for servers that declared `listChanged` (bridge: `false`). (F-75)
- Extensions (tasks, UI): opt-in. (changelog Minor 1)
- `subscriptions/listen`: **open decision** (F-103). Spec text does not explicitly require a server
  with no notifiable features to implement it; -32601 is defensible per `MethodNotFoundError`
  ("a client invokes a method the server does not implement"), while the "message patterns MUST be
  supported" sentence (F-1) argues for a minimal ack-and-hold implementation. Recommendation: minimal
  implementation is low-cost (ack with `notifications:{}` and `_meta.subscriptionId`, keep open,
  drop on `notifications/cancelled`, send completion result + `notifications/cancelled` on shutdown —
  F-104/F-105) and removes the ambiguity.

**Open decisions to record in the design**
- D1 (F-41): contents of `supportedVersions` / `data.supported` — modern only (`["2026-07-28"]`,
  matches the discover example and "choose a version … for use in subsequent requests") vs. also
  legacy versions (matches the -32022 examples). And what to answer to a `_meta` request whose
  version is a legacy one (recommended: -32022, consistent with listing only modern versions).
- D2 (F-103): `subscriptions/listen` minimal vs -32601.
- D3: `ttlMs` value (0 vs a positive TTL) given that tools can change with config but `listChanged`
  is `false`.
- D4 (F-93): validate `logLevel` values (-32602) or ignore the key.
